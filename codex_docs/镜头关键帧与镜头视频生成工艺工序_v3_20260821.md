## 0. 文档目的

本文定义《青山》短剧生产线中以下两个核心环节的完整工艺和工序：

1. 镜头关键帧生成。
2. 镜头视频生成。

本文用于：

- Roger 人工审核生产线是否正确。
- 外部 AI 对流程、数据合同、门禁和异常路径做独立检查。
- Codex、Claude、Writer Agent、Pipeline Agent、后期 Agent、QA Agent 之间统一事实源。
- 防止缺资产、空间错位、动作合同矛盾、重复付费、错误重掷和技术检查冒充内容准入。

本文不是提示词范例合集，也不是单集 E40 的临时执行记录。它是生产线工艺定义。

v3.4 修订摘要：修复“任务携带 native-registry 原图但供应商仍重塑人物脸”的基础契约缺口。生产线不再把“参考图字节已发送”解释为“身份已锁定”；所有可见人物任务必须声明身份传输模式、逐图角色标签和身份权威映射。当前 GPT Image/Giggle 适配器只有扁平软参考能力，没有 provider-native 身份锁，因此必须使用带标签的软传输并强制 exact-output InsightFace 身份门，或使用单人物 identity plate / 本地 exact-pixel 合成路线。`HUMAN_AND_AI` 标签不得绕过 P0 客观验证。

## 1. 权威顺序

发生冲突时按以下顺序执行：

1. Roger 最新明确授权。
2. `canonical` 剧本、manifest 和本集锁定状态。
3. `configs/GATE_REGISTRY_v3_20260716.json` 中已注册 gate。
4. 本文定义的生成合同。
5. `agent_factory/AGENTS.md` 的生产执行规则。
6. 工具默认值和供应商技能说明。

项目级规则覆盖供应商技能默认值。虽然通用 Giggle 技能可能示例使用其他 Seedance 型号，但本生产线 E40 及以后只允许：

```text
seedance-2.0-fast
720p
```

禁止：

- `seedance-2.0-pro`
- `seedance-2.0-mini`
- 未明确版本的 `seedance-2.0`

这里的“只允许”是当前付费执行策略，不是把工艺绑定死在 Seedance。生产线先生成供应商无关合同，再通过 capability registry 和 adapter 映射到具体模型。当前兼容槽包括：

- 视频：Seedance 2 Fast（已部署）；Sora 2、Kling、H3、Wan 2.7（合同兼容，待 provider model_id、凭据、能力探针与成本授权）。
- 图片：GPT Image 2 Pro（已部署）；SD2、Seed Image、Google Nano Banana（含 `nanubanner` 别名；合同兼容，待部署参数）。

兼容槽不等于付费授权。未部署模型只能运行 `COMPATIBILITY_CHECK`，不得通过 `PAID_SUBMIT`。

## 2. 核心原则

### 2.1 单一事实源

以下信息不得分别在提示词、表格和代码里各写一套：

- 人物和道具数量。
- 空间关系。
- 起始站位。
- 动作终态。
- 运动轨迹。
- 物理后果。

必须先形成结构化合同，再由编译器生成提示词。提示词是合同的派生物，不是新的事实源。

### 2.2 资产库优先

生成关键帧前必须先查资产库。禁止先生成一张“差不多”的角色或道具，再让 QA 判断是否像原资产。

```text
canonical entity ID
→ 原生注册表
→ 锁定状态
→ generation reference
→ 文件 SHA
→ QA/准入证据
→ 本次 reference transport
```

### 2.3 先空间，后站位，再动作

固定解析顺序：

```text
EPISODE-GLOBAL-SPACE-MAP-ID
→ GLOBAL-SPACE-MAP-ID
→ SUBSPACE-ID
→ ZONE/ANGLE/AXIS
→ 人物与物品起始站位
→ 动作终态
→ 动作轨迹
```

缺任一层，不得付费生成关键帧或视频。

### 2.4 事前门优先

能在提交前机械发现的问题，禁止留到生成后靠 Q1/Q2 发现。

事前门负责检查输入是否完整和合同是否自洽；Q1/Q2 负责检查生成内容是否真的符合合同。两者不能互相替代。

### 2.5 技术通过不等于内容准入

以下状态只说明文件可读取：

```text
TECHNICAL_PASS_CONTENT_UNREVIEWED
```

它不代表人物、场景、动作、时代或画面内容正确。

### 2.6 已绑定任务不可改写

任务一旦绑定真实 `task_id`：

- 不修改当次提示词。
- 不修改输入图片。
- 不替换 model。
- 不用同一任务键重新 POST。
- 新合同只作用于新任务键。

### 2.7 模型可移植性

canonical 实体、原生资产 lineage、空间三级链、blocking、动作终态、轨迹、真人表演和 Q1/Q2 判据属于生产线，不属于供应商。模型适配器只负责字段映射、能力校验和当前集付费授权；能力未知、凭据缺失或 provider model_id 未锁定时必须 fail closed。切换模型不得复制一套弱化合同，也不得绕过事务、重试、QA 或资产门。

## 3. 参与 Agent 与职责

| Agent/工位 | 主要职责 | 不得承担的职责 |
|---|---|---|
| Writer Agent | 输出 canonical 剧本动作、角色、道具、对白、镜头意图 | 不直接提交付费生成 |

| Spatial Planner | 建立整集地图、地点地图和镜头子空间 | 不直接决定人物身份 |
| Keyframe Compiler | 把结构化合同、资产和真人提示词编译成关键帧任务 | 不自行新增人物、道具或剧情 |
| Video Action Compiler | 从起始状态、终态、轨迹和时间窗口编译视频提示词 | 不在自由文本里另写一套动作事实 |

## 4. 数据对象与 ID 层级

### 4.1 剧集与镜头

| 字段 | 说明 |
|---|---|
| `episode` | 集号，如 `E40` |
| `unit_id` | 镜头或动作单元，如 `R03` |
| `task_key` | 唯一任务键，不得通过改版本号绕过重试规则 |
| `canonical_script_action` | canonical 剧本动作原文 |
| `source_script_sha256` | 剧本文件或动作合同 SHA |

### 4.2 资产 ID

| 类型 | 示例 | 注册源 |
|---|---|---|
| 角色 | `CHAR-陈迹-古装` | series character registry |
| 道具 | `PROP-E40-FOUR-FROST-MARKS` | series/episode prop registry |
| 场景 | `GSM-WANGFU-HALL-001` | scene/global-space authority |

### 4.3 空间 ID

| 层级 | 示例 | 作用 |
|---|---|---|
| 整集全局空间图 | `EGSM-E40-WANGFU-SEQUENCE-001` | 覆盖本集全部地点及连接关系 |
| 地点全局空间图 | `GSM-WANGFU-HALL-001` | 可跨集继承的地点拓扑 |
| 镜头子空间 | `SUBSPACE-E40-R03` | 当前镜头可见和可行动区域 |
| 区域 | `ZONE-*` | 人物、道具与路径坐标区域 |
| 机位 | `ANGLE-*` | 镜头视点 |
| 轴线 | `AXIS-*` | 180 度关系、人物左右和运动方向 |

## 5. 镜头关键帧生成工艺

### KF-00：读取当前活动集

输入：

- `workflow/work_queue.json`
- 对应集 task-lane scheduler
- canonical/manifest
- 最近三条生产回执
- 积分事务和真实本机/远端状态

输出：当前可执行关键帧单元列表。

禁止：从历史集、旧回执或聊天记忆写死当前集号。

### KF-01：解析 canonical 镜头实体

每镜必须结构化声明：

```json
{
  "canonical_characters": [],
  "visible_characters": [],
  "canonical_props": [],
  "canonical_script_action": "",
  "shot_purpose": ""
}
```

规则：

- `visible_characters` 是本镜允许入画角色。
- canonical 但不入画的角色只能用于连续性传递，不得被模型画入镜头。
- 禁止从自由提示词反向猜测实体。

### KF-02：角色资产解析

角色解析顺序：

1. 查 `configs/series_character_asset_registry_20260712.json`。
2. 状态必须以 `LOCKED` 开头。
3. 优先读取 `generation_reference_image`。
4. 其次读取 identity/reference image。
5. 校验声明 SHA 与实际 SHA。
6. 绑定 generation reference QA。
7. 未找到时，只允许使用已准入的本集新资产。
8. 仍未找到则阻断。

允许的资产来源：

```text
CANONICAL_NATIVE_REGISTRY
ADMITTED_PRIOR_EPISODE_NATIVE
EPISODE_NEW_ASSET
```

禁止：

- 用旧视频截图替代角色原图，除非该截图已经正式注册。
- 用本集临时关键帧反向覆盖系列角色身份。
- 用“长得像”作为资产准入证据。

### KF-03：道具资产解析

道具必须通过 prop registry 解析，而不是在 builder 中硬编码路径。

每个道具条目至少包含：

```json
{
  "status": "LOCKED_*",
  "generation_reference_image": "...",
  "generation_reference_sha256": "...",
  "generation_reference_qa": "...",
  "semantic_lock": "可选但推荐"
}
```

`semantic_lock` 用于明确道具的真实语义。例如：

```text
四处霜痕 = 木面上四块扁平、不规则霜残留
不是四个立体物件
不是微缩建筑
不是雕花构件
```

综合图只允许承担运输作用。综合图不能替代每个 source component 的路径、SHA 和 QA。

### KF-04：场景和空间图解析

每镜必须绑定且按固定顺序传输：

1. 整集全局空间图。
2. 地点全局空间图。
3. 镜头子空间图。
4. 人物锚。
5. 道具锚。
6. 场景视觉参考。

必须验证：

- 三层空间 ID 完整。
- 声明的空间图 SHA 与实际文件一致。
- 子空间确实继承整集和地点地图。
- 机位、轴线、固定建筑元素一致。

### KF-05：起始站位与动作终态设计

关键帧任务必须有：

```json
{
  "blocking": {
    "characters": [],
    "props": []
  },
  "action_end_blocking": {
    "characters": [],
    "props": []
  },
  "trajectory_overlays": []
}
```

`blocking` 只描述第一帧已经存在的状态。

`action_end_blocking` 只用于后续动作设计，不能提前画进关键帧。

`trajectory_overlays` 至少说明：

- `entity_id`
- 起点
- 终点
- 运动动作
- 接触/交汇关系
- 可见物理后果

### KF-06：镜头摄影合同

必须确定：

- 9:16 画幅。
- 景别。
- 机位高度与角度。
- 镜头焦段意图。
- 景深。
- 现场动机光。
- 180 度轴线和 eyeline。
- 哪些固定空间元素必须可见。

禁止用“电影感、唯美、高级”替代具体镜头设计。

### KF-07：真人面孔与微表演合同

有可见人物的新关键帧必须注入 `human_realism_contract v1.0.0`。

合同至少覆盖：

- 身份与年龄优先于漂亮。
- 毛孔、细汗毛、唇纹、轻微肤色差。
- 眼球湿润反光。
- 轻微面部不对称。
- 真实 35/50/85mm 光学。
- 场景内动机光。
- 事件刺激。
- 视线落点。
- 一至两个面部区域的微变化。
- 呼吸、吞咽、肩颈、重心或手指张力支持。
- 情绪结束后的残余状态。

禁止：

- AI 标准微笑。
- 同时挑眉、瞪眼、张嘴。
- 玻璃眼、塑料皮、蜡像脸。
- 磨皮、美颜和网红摆拍。
- 所有面部区域同步等幅运动。

无人脸镜头仍应执行真实材质、曝光、空气透视和自然动态范围规则。

### KF-08：参考图运输

参考图运输必须区分三个事实，禁止混写：

1. 原图文件和 SHA 已被解析；
2. 原图字节已发送给供应商；
3. 供应商是否支持角色语义与身份锁。

当前 `gpt-image-2-pro` Giggle 接口只支持扁平 `reference_images`。它能传输原图字节，但不传输 `role/entity_id/identity_authority`，也没有 provider-native identity lock。因此，可见人物任务必须带：

```json
{
  "identity_reference_transport": {
    "schema": "qingshan.identity_reference_transport.v1",
    "mode": "LABELED_FLAT_REFERENCE_WITH_EXACT_OUTPUT_GATE",
    "transport_guarantee": "SOFT_REFERENCE_REQUIRES_EXACT_OUTPUT_GATE",
    "output_identity_verification_method": "INSIGHTFACE_COSINE_V1",
    "exact_output_sha_required": true,
    "authority_map": {"CHAR-*": "@图片N"},
    "authority_prompt_token": "本任务唯一身份权威块的稳定 token"
  }
}
```

对应 `reference_image_sequence` 的人物行必须声明：

```json
{
  "asset_label": "@图片N",
  "role": "character",
  "entity_id": "CHAR-*",
  "identity_authority": "PRIMARY_NATIVE_REGISTRY"
}
```

提示词必须逐项写清：哪一张只定义人物脸，哪些图片只定义空间/场景/道具且不得平均、混合或重塑人物身份。上述映射只能提高供应商服从度，不能被当作输出身份 PASS。

允许的另外两种路线：

- `IDENTITY_ONLY_PLATE`：仅一个人物的 native-registry 身份参考，不混入场景、空间或道具图片；用于先做身份板。
- `PROVIDER_NATIVE_IDENTITY_LOCK`：只有 capability registry 明确证明当前 provider 支持角色语义传输和原生身份锁时才允许；当前 GPT Image/Giggle 配置不支持。

旧式“空间图、场景图、人物图混入普通数组，再写一句不得换脸”的任务必须在付费事务创建前失败，失败码包括 `IDENTITY_REFERENCE_TRANSPORT_NOT_DECLARED` 或 `IDENTITY_AUTHORITY_LOST_IN_FLAT_REFERENCE_TRANSPORT`。

供应商参考图数量受限时，可以制作机械 contact sheet，但必须保留：

```json
{
  "path": "transported contact sheet",
  "sha256": "transport SHA",
  "source_component_path": "native source",
  "source_component_sha256": "native source SHA",
  "qa_report": "source QA",
  "asset_origin": "registry origin",
  "entity_id": "canonical entity",
  "role": "character/prop/..."
}
```

contact sheet 只减少运输图片数量，不创建新的角色或道具权威。

### KF-09：关键帧提示词编译

提示词必须由结构化字段编译，并按以下顺序表达：

1. 用途和画幅。
2. canonical 剧本动作原文。
3. 空间继承链。
4. 房间、区域、机位、轴线。
5. 固定空间元素。
6. 起始人物站位。
7. 起始道具站位。
8. 动作终态，仅用于轨迹预留。
9. 轨迹权威。
10. 允许入画角色。
11. 输入参考用途。
12. 真人面孔和微表演合同。
13. 负面约束。

关键帧只画动作起始瞬间，不画完整动作过程。

### KF-10：付费前输入完整性门

机械检查：

```text
canonical_characters ∪ canonical_props
⊆ 本次 reference_image_sequence 中已绑定实体
```

同时必须检查语义证据：

- source component 文件存在。
- source component SHA 一致。
- QA 证据文件存在。
- `asset_origin` 在允许列表。
- contact sheet 没有抹掉 source component lineage。

失败码：

```text
CANONICAL_ENTITY_DECLARATION_MISSING
MISSING_ANCHOR_FOR_CANONICAL_ENTITY
SEMANTIC_ANCHOR_EVIDENCE_MISSING
SEMANTIC_ANCHOR_EVIDENCE_INVALID
```

这些失败发生在付费 POST 前，不产生生成费用。

### KF-11：关键帧任务身份指纹

`input_template_id` 至少由以下信息计算：

- 空间链 ID。
- reference role/entity 规格。
- prompt template/contract version。
- 角色集合。

用途：

- 聚合同模板重复失败。
- 判断是否是系统性输入缺陷。
- 不用于制造串行金丝雀。

### KF-12：关键帧付费事务

提交顺序不可颠倒：

```text
生成 fingerprint
→ 检查无既有 paid candidate
→ 写 durable transaction
→ 执行 provider POST
→ 立即绑定 task_id
→ 写提交回执
```

若 POST 返回超时但 task_id 已绑定，必须查询原 task_id，禁止再次 POST。

### KF-13：关键帧并行提交

每个独立镜头是独立 provider-bound 工位。

规则：

- 镜头内部依赖串行。
- 不同镜头并行。
- 一个镜头失败不能冻结其他镜头。
- 相同模板用于失败归因，不形成全局屏障。
- 提交后继续音频、字幕、下一镜预制和已准入前缀总装。

### KF-14：关键帧收割

完成项立即：

1. 下载原图。
2. 保存 provider 原始回执。
3. 计算文件 SHA。
4. 记录 task_id、文件路径、字节数和扣费状态。
5. 进入 Q1。

失败项立即：

1. 记录权威终态。
2. 查询 Pay/Refund。
3. 分类净扣费。
4. 写失败原因。
5. 不自动假设“失败未扣费”。

### KF-15：关键帧 Q1 正式准入

Q1 必须基于同一张原分辨率图片的准确 SHA，依次通过：

1. `CHARACTER-IDENTITY-ADMISSION`
2. `SCENE-AUTHORITY-LOCK`
3. `ACTION-SHOT-DESIGN-AND-STATE-HANDOFF`
4. `PERIOD-ANACHRONISM-LOCK`

必须有原分辨率内容审看。P0 不是审美判断，必须回答由 canonical 合同派生、能够复算的客观问题：

- 身份：`INSIGHTFACE_COSINE_V1` 对 canonical 至少三视图与每源至少三张输出抽帧做 exact-SHA 比对；分数达到注册 PASS 阈值可自动准入，落入注册边界带才转人工仲裁。`HUMAN`、`AI_VISUAL`、`HUMAN_AND_AI` 都必须携带同一客观验证载荷，reviewer 标签本身不能代替身份比对。
- 年代：闭集禁品检测与 OCR 伪文字结构化结果，不接受自由文本“看起来没问题”。
- 动作终态与实体数量：VLM 结构化问答逐项回答人物/道具数量、左右、接触点、物品归属和终态；答案必须绑定输出 SHA。

人只保留三处：边界带仲裁、周期性抽样校准阈值、发行前整集观看。边界带人工仲裁最长等待 15 分钟；超时后以注册中点 `0.375` 自动裁决：分数位于中点及以上执行 `ADMIT_BEST_EFFORT` 并记 `ADMITTED_WITH_P2`，低于中点执行 `SWITCH_COVERAGE`。回执必须保存原始 aggregate、请求时间、超时事实和裁决方向。缺机器运行时、缺 exact SHA、缺注册阈值或仅有自报 PASS 时均不得自动准入。

未注册判据自动降级为 diagnostic，不能阻断。

Q1 合法终态：

```text
status = ADMITTED | ADMITTED_WITH_P2
downstream_status = ADMITTED_FOR_VIDEO_SUBMIT
```

其他状态均不得进入视频生成。

## 6. 镜头视频生成工艺

### VD-00：读取 Q1 准入关键帧

视频任务必须绑定：

- Q1 admission 路径。
- Q1 asset SHA。
- 实际首帧文件路径。
- 首帧文件 SHA。
- 原始 RGB SHA，可用时必须记录。

四个 SHA/路径关系必须一致。

### VD-01：模型与参数锁

E40 及以后固定：

```json
{
  "model": "seedance-2.0-fast",
  "resolution": "720p",
  "aspect_ratio": "9:16",
  "duration_seconds": "4-15 的整数",
  "generating_count": 1
}
```

默认模式：

```text
image-to-video / exact first frame
```

多模态图片最多 9 张；实际生产取供应商限制和项目限制中更严的一侧。

### VD-02：视频首帧语义权威

视频阶段不要求重新把每个角色、道具原图都冒充视频首帧。

视频语义权威来自：

```text
原生资产
→ 关键帧输入门
→ 关键帧生成
→ 原分辨率 Q1
→ Q1 准入首帧
```

视频付费前必须验证：

- Q1 状态为 `ADMITTED` 或 `ADMITTED_WITH_P2`。
- Q1 downstream 为 `ADMITTED_FOR_VIDEO_SUBMIT`。
- Q1 `asset_sha256` 与视频 exact-first-frame SHA 相同。

失败码：

```text
Q1_ADMITTED_START_FRAME
Q1_ADMISSION_UNREADABLE
Q1_START_FRAME_NOT_ADMITTED
Q1_DOWNSTREAM_STATUS_INVALID
Q1_START_FRAME_SHA_MISMATCH
```

### VD-03：继承空间链

视频必须继承关键帧相同的：

- `episode_global_space_map_id`
- `global_space_map_id`
- `subspace_id`
- `space_chain_id`
- camera/axis

视频提示词不能改变房间拓扑、人物左右、出入口或固定建筑关系。

### VD-04：结构化动作合同

每个动作视频必须提供：

```json
{
  "blocking": {},
  "action_end_blocking": {},
  "trajectory_overlays": [],
  "performance_tempo_contract": {
    "playback_speed": "REAL_TIME_1X",
    "atomic_action_windows": []
  },
  "camera_contract": "",
  "forbidden_generation": []
}
```

动作合同必须检查：

- 起始状态存在。
- 动作终态存在。
- 轨迹存在。
- 所有 canonical 实体至少在起始或终态出现。
- 每条轨迹 entity 必须属于 canonical。
- 每条轨迹必须有起点、终点、动作和可见后果。
- 空间链至少包含整集、地点和子空间三级。
- 至少一个动作时间窗口。

失败时：

```text
BLOCK_STRUCTURED_ACTION_CONTRACT_INVALID
```

不得付费 POST。

### VD-05：动作因果设计

每镜动作至少包含：

```text
发起者
→ 目标
→ 起始姿态/接触点
→ 行进路径
→ 对方反应
→ 可见物理后果
→ 明确终态
```

战斗镜头额外必须包含：

- 攻击意图。
- 防御反应。
- 胜负或控制关系。
- 失败方身体/物体结果。
- 不得只写“激烈打斗”。

### VD-06：按镜头类型分离动作时间模板

对白/情绪镜保留三段式：起意/表达、主要表演、余韵与自然沉降。该模板不得套用到打斗镜。

打斗镜使用专用合同：

```text
接触发生：≤0.2 秒
第一回合完成：≤1.5 秒
同一成片短镜：命中或动作结论处即切，不演长余震
生成单元：8–15 秒，连续编排 3–4 个攻防回合
剪辑消费：每个生成单元拆成 4–6 个有动机短镜
```

生成时长不等于成片镜头时长。禁止把 Seedance 的 4 秒供应商下限当成成片镜头长度，也禁止“一拳后站着喘两秒”。打斗场同时接入既有呼吸结构：至少三轮“爆发 2–4 秒、逐秒运动量 ≥10”与“蓄势 1–2 秒”交替；匀速快切不合格。

`0.2/1.5 秒` 是已采用的打斗编译合同，只对显式声明且与 canonical 匹配的 `shot_type=COMBAT` 生效；对白/情绪镜不受其约束。`shot_type` 缺失必须失败，canonical 单元含 `△【打斗·…】`、`FS-1 完整打斗` 或 `FS-1 窗口锚` 时非 COMBAT 声明必须失败，反向误标同样失败。不得用 `shot_class` 或 GENERAL 缺省绕过。未注册的派生审美数值仍为 diagnostic，不得另造新门。

### VD-07：视频提示词编译

提示词由 `action_video_prompt_compiler v2.0.0` 生成，顺序为：

1. exact first frame 声明。
2. 空间继承链。
3. 固定机位和轴线。
4. 起始状态。
5. 逐实体轨迹。
6. 动作终态。
7. 时间窗口。
8. 唯一物理因果声明。
9. 禁止项。

人工可以补充：

- 表演质感。
- 摄影质感。
- 声音和对白。

人工不得重新定义：

- 人物和道具数量。
- 运动方向。
- 接触点。
- 终态。

### VD-08：对白和声音

无原生对白的视频：

```text
dialogue_transport = SILENT_VISUAL_POST_DUB
```

有对白的视频必须明确：

- 说话人。
- 准确台词。
- 情绪和视线对象。
- 台词必须在本镜说完。
- 说完后至少短暂停顿再切。
- 非说话人仍有倾听和呼吸反应。

画面提示与音频提示必须逻辑分离，字幕不得由模型直接画进视频。

### VD-09：视频付费前门

按顺序检查：

1. model 白名单。
2. 720p、9:16、4–15 秒整数。
3. Q1 exact-SHA 首帧准入。
4. canonical 实体声明。
5. 语义首帧权威。
6. 三层空间链。
7. 起始/终态/轨迹合同。
8. 提示词合同。
9. 重试次数。
10. 预算和成本门。
11. 是否已存在同 fingerprint 的付费任务。

任何一项失败均不得 POST。

### VD-10：视频付费事务

顺序：

```text
计算 generation fingerprint
→ 查既有 paid candidate
→ 写 durable transaction
→ POST
→ 立即绑定 task_id
→ 写提交回执
```

默认付费入口：durable transaction submitter。

Chrome 只用于无等价 API 的人工界面流程或只读排障，不能成为第二个付费入口。

### VD-11：并行生成

并行原则：

- 独立镜头并行。
- 首尾帧依赖链内部串行。
- 一个镜头远端等待时继续其他镜头、音频、字幕和预制。
- 一个镜头失败只隔离自身。
- 已准入前缀允许做剪辑预组装。

真实活跃必须绑定：

- 真实 `remote_task_id`，或
- 真实本机产出进程。

禁止用审计、观察、watchdog 或空复核任务伪造活跃。

### VD-12：远端收割

每轮先收割所有已绑定 task_id：

1. 查询状态。
2. 完成则立即下载。
3. 失败则读取 provider 原因。
4. 查询精确 task_id 的 Pay/Refund。
5. 计算输出 SHA。
6. 完成项立即进入技术 QA 和 Q2。

不得重复 POST。

### VD-13：技术 QA

技术 QA 至少包括：

- 文件存在。
- 可解码。
- 时长正确。
- 分辨率和画幅正确。
- 帧率可用。
- 音视频流结构可用。
- 无严重坏帧或周期性重复帧。

技术通过只能写：

```text
TECHNICAL_PASS_CONTENT_UNREVIEWED
```

### VD-14：首帧一致性检查

检查：

- 视频第 0 帧与输入关键帧的一致性。
- 第 0 帧到第 1 帧没有突然变脸、换装或换空间。
- 不允许用后期单帧替换伪造首帧一致。

可记录的指标包括 SSIM、MAE、pHash，但未经注册的数值审美指标只能作为 diagnostic，不能单独阻断。

### VD-15：视频 Q2 正式准入

视频 Q2 必须基于准确视频 SHA，通过：

1. `CHARACTER-IDENTITY-ADMISSION`
2. `SCENE-AUTHORITY-LOCK`
3. `ACTION-SHOT-DESIGN-AND-STATE-HANDOFF`
4. `PERIOD-ANACHRONISM-LOCK`
5. `DEFECT-TIER-TOLERANCE`

原分辨率审看必须确认：

- 人物身份和年龄稳定。
- 空间和轴线稳定。
- 动作真正发生并完成。
- 动作因果与剧本一致。
- 道具数量、方向和终态正确。
- 物理接触和遮挡合理。
- 微表演有刺激、视线和身体支持。
- 无现代物、伪文字、字幕、水印。
- 缺陷等级正确。

P0 类判据必须由可复算的客观证据出具；达到注册强 PASS 阈值的机器证据可自动准入，边界带才由 `HUMAN` 或 `HUMAN_AND_AI` 仲裁。`AI_VISUAL` 自由文本或未绑定 SHA 的自报 PASS 不得准入。

Q2 合法终态：

```text
status = ADMITTED | ADMITTED_WITH_P2
downstream_status = ADMITTED_FOR_ASSEMBLY
```

只有该状态允许总装。

## 7. 缺陷分级

### P0

必须阻断：

- 错人物或身份明显漂移。
- 核心剧情动作相反或未发生。
- 空间关系破坏剧情因果。
- 缺失核心人物或道具。
- 多出会改变剧情的实体。
- 严重时代错误。
- 文件损坏或无法使用。

### P1

通常阻断：

- 动作终态不清楚。
- 核心道具数量或方向错误。
- 人物连续性明显断裂。
- 严重穿模、复制或肢体错误影响叙事。
- 视线、轴线错误导致关系读反。

### P2

可以在登记后条件准入：

- 不影响身份、剧情和动作读取的轻微边缘问题。
- 短暂、非核心区域的小瑕疵。
- 已在缺陷预算内并可由剪辑遮盖的问题。

未注册的像素比例、骨架、厘米级间隙、接触点数量等判据默认是 diagnostic，不能自行升级为 P0/P1。

## 8. 失败归因与修复路线

| failure attribution | 根因 | 允许修改 | 禁止行为 |
|---|---|---|---|
| `MISSING_REFERENCE_ANCHOR` | 缺原生锚或锚未传输 | `REFERENCE_ANCHORS` | 只改提示词重掷 |
| `PROMPT_SEMANTICS` | 提示词语义错误 | `PROMPT` | 输入不变反复重掷 |
| `SPACE_CHAIN_MISMATCH` | 地图、子空间或轴线错误 | `SPACE_CHAIN` | 用后期伪装修复空间 |
| `CANONICAL_MISMATCH` | canonical 本身矛盾 | `QA_TARGET/canonical` | 直接媒体重掷 |
| `MODEL_STOCHASTIC` | 输入正确但随机失败 | 输入保持不变的受限重试 | 借机改剧情或实体 |
| `PROVIDER_TIMEOUT` | 供应商超时 | 先查退款，再创建合规新任务 | 未分类扣费就重复 POST |
| `TEMPLATE_DEFECT` | 同一 `input_template_id` 下至少 2 个单元同因失败 | 在模板层修一次，尚未裁决单元统一挂起，修复后整组一次性并行重掷 | 为同一模板根因逐单元分别付费重掷 |

同一失败归因连续两次时，应进入模板缺陷或 coverage 切换判断，不继续盲目重掷。

Q2 判为 P1 后、进入付费重掷前，必须先经过 `ZERO_COST_REMEDY_ATTEMPTED` 工序位：裁切、调色、换帧、遮罩或等价剪辑能解决的先零成本修复；确认修不动后才消耗重掷配额。P0 不得靠遮盖凑合准入。

## 9. 重试、预算与人工例外

默认规则：

- 同一镜头最多尝试 3 次付费生成。
- 单集付费重掷不超过该集付费任务数的 15%。
- 不得用新版本号绕过。

重试前必须同时满足：

1. 原任务权威终态。
2. Pay/Refund 已分类。
3. 失败原因已登记。
4. 提示词记忆已写入，适用时执行。
5. 修复变量与失败归因匹配。
6. 新任务 fingerprint 与旧任务不同，除受限随机重试外。

人工预算例外必须有：

- 明确授权引用。
- 最大 credits。
- 适用镜头范围。
- 新任务数量上限。
- 不取消已绑定任务。
- 每次新 POST 仍执行事务先行。

人工预算例外不是取消 QA、模型白名单或重复提交保护。

## 16. 当前已知边界

1. 机械语义门能验证资产来源、SHA、QA 和 lineage，但不能仅凭 JSON 判断图片视觉内容真的正确；图像语义最终仍由资产准入和原分辨率 Q1/Q2 负责。
2. contact sheet 是供应商图片数量限制下的运输工具，可能降低模型对单一实体的注意力；关键角色或关键道具应尽量使用独立参考图。
3. 结构化动作编译器能阻止数量、路径和终态缺失，但复杂表演节奏仍需导演或视觉 QA 判断。
4. runtime registry 不包含在公共代码 Release 中；换机部署必须单独同步私有资产与 SHA/QA 证据。
5. 历史已绑定任务不受新合同追溯改写；其结果必须按当时输入做诚实 QA，失败后用新任务键进入新合同。
